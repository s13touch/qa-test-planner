# QA Test Planner

Комплексный скилл для QA-инженеров: создание тест-планов, генерация ручных тест-кейсов, построение регрессионных наборов, валидация дизайна по Figma и структурированные баг-репорты.

## Назначение

Скилл помогает QA-специалистам быстро и единообразно создавать документы тестирования. Он убирает ручную рутину по оформлению тест-планов, тест-кейсов и баг-репортов, применяя единые шаблоны и лучшие практики покрытия, репортинга и валидации дизайна.

## Когда использовать

Используйте скилл, когда нужно:
- составить тест-план на новую фичу или релиз;
- сгенерировать ручные тест-кейсы;
- собрать регрессионный набор (smoke, targeted, full);
- валидировать UI по макетам Figma;
- задокументировать баги с понятными шагами;
- задать единые стандарты тестирования в команде.

### Активация

Скилл использует **явный вызов** — должен быть назван по имени:

```
/qa-test-planner
qa-test-planner
используй скилл qa-test-planner
```

## Как это работает

Три фазы:

### 1. Анализ
- Разбирает описание фичи или требования.
- Определяет нужные типы тестов (функциональные, UI, интеграционные и т.д.).
- Определяет объём, приоритеты и крайние случаи.

### 2. Генерация
- Создаёт структурированные результаты по проверенным шаблонам.
- Автоматически применяет лучшие практики QA.
- Включает крайние случаи и вариации.
- Организует контент для удобного выполнения и отслеживания.

### 3. Валидация
- Проверяет полноту документа.
- Проверяет трассируемость между требованиями и тестами.
- Следит за понятностью и выполнимостью шагов.

## Ключевые возможности

### 1. Тест-план
Полный тест-план: краткое резюме, объём (входит/не входит), стратегия, тестовое окружение, критерии входа/выхода, оценка рисков, артефакты.

### 2. Ручные тест-кейсы
Тест-кейсы в виде **единой таблицы** (см. «Форматы вывода»): № требования, номер кейса (`TC-XX`), приоритет, краткое описание сценария.

### 3. Регрессионные наборы
Уровневые наборы: **Smoke** (15–30 мин), **Targeted** (30–60 мин), **Full** (2–4 ч), **Sanity** (10–15 мин).

### 4. Валидация Figma
Интеграция с Figma MCP: извлечение спецификаций (цвета, отступы, типографика), сравнение реализации с дизайном, чек-листы UI-тестов, фиксация визуальных расхождений как багов.

### 5. Баг-репорты
Структурированный баг-репорт: заголовок «что + где + при каких условиях», окружение, описание, таблица «Шаги → Фактический результат → Ожидаемый результат», визуальные доказательства, доп. контекст.

## Примеры использования

### Пример 1: тест-план
```
/qa-test-planner
Составь тест-план для функции авторизации
```
Результат: тест-план по нашему шаблону (резюме, объём, стратегия, окружение, критерии, риски, артефакты).

### Пример 2: тест-кейсы
```
/qa-test-planner
Сгенерируй тест-кейсы для оформления заказа
```
Результат: таблица тест-кейсов по разделам источника.

### Пример 3: регрессионный набор
```
/qa-test-planner
Собери smoke-набор для модуля оплаты
```
Результат: приоритизированный набор критичных путей.

### Пример 4: валидация Figma
```
/qa-test-planner
Сравни страницу входа с макетом Figma по [URL]
```
Результат: чек-лист сравнения (размеры, цвета, типографика, отступы, состояния) + тест-кейсы.

### Пример 5: баг-репорт
```
/qa-test-planner
Создай баг-репорт: форма отправляется с пустым email
```
Результат: баг-репорт по нашему шаблону.

## Справочники

- `references/test_case_templates.md` — наш табличный формат тест-кейсов, типы, приоритеты.
- `references/bug_report_templates.md` — наш формат баг-репорта, правило заголовка, серьёзность.
- `references/regression_testing.md` — стратегии регрессии.
- `references/figma_validation.md` — валидация дизайна.

## Стандарты качества

### Чек-лист тест-плана
- Объём чётко определён (входит/не входит).
- Заданы критерии входа/выхода.
- Риски выявлены с митигациями.
- Сроки реалистичны.

### Чек-лист тест-кейсов
- Одна строка = один кейс в таблице.
- Сквозная нумерация `TC-01`, `TC-02`, …
- Приоритет `P0–P3` назначен.
- Описание — одно краткое предложение.

### Чек-лист баг-репорта
- Заголовок отвечает на «что / где / при каких условиях».
- Заполнена таблица «Шаги → Фактический → Ожидаемый».
- Окружение задокументировано.
- Приложены скриншоты/доказательства.
- Заданы серьёзность и приоритет.

## Антипаттерны

| Избегайте | Почему плохо | Как надо |
|-------|--------------|-------------------|
| Размытые шаги теста | Невозможно воспроизвести | Конкретные действия + ожидаемый результат |
| Отсутствие предусловий | Тесты неожиданно падают | Описывать все требования к настройке |
| Нет тестовых данных | Тестировщик заблокирован | Давать примеры данных |
| Общие заголовки багов | Трудно отслеживать | Заголовок «что + где + при каких условиях» |
| Пропуск крайних случаев | Пропуск критичных багов | Граничные значения, null, пустые состояния |

## Интеграция с Figma MCP

При настроенном Figma MCP скилл может:
1. извлекать спецификации из Figma-ссылок;
2. генерировать точные UI-тест-кейсы;
3. сравнивать реализацию с дизайн-токенами;
4. создавать баг-репорты со ссылками на Figma.

## Лучшие практики

### Написание тест-кейсов
- Быть конкретным и однозначным.
- Один кейс — одна проверка.
- Сквозная нумерация `TC-XX`.
- Поддерживать актуальность при изменениях фич.

### Баг-репортинг
- Понятные шаги воспроизведения.
- Скриншоты, видео или логи консоли.
- Точные детали окружения.
- Ссылка на Figma для UI-багов.

### Регрессионное тестирование
- Регулярно поддерживать набор.
- Приоритизировать критичные пути.
- Часто запускать smoke-тесты.
- Обновлять набор после каждого релиза.

## Форматы вывода

### Тест-кейсы

Вход — любая документация (требования, спеки, user stories, дизайн, тикеты, заметки). Кейсы группируются по разделам источника (названия сохраняются), каждый раздел — заголовок + таблица из 4 колонок:

*Название раздела*

| № требования | Номер кейса | Приоритет | Описание тест-кейса |
| ------------ | ----------- | --------- | ------------------- |
| 12 | TC-01 | P0 | При нажатии на кнопку "Заключить договор" открывается модальное окно "Заключение договора". |

- `№ требования` — как в источнике; если нумерации нет — ссылка на раздел/историю/тикет или `—`.
- `Номер кейса` — сквозной `TC-01`, `TC-02`, … по всем разделам.
- `Приоритет` — `P0 | P1 | P2 | P3`.
- `Описание тест-кейса` — одно краткое предложение; можно префиксовать `[EP]` или `[BVA]`.

Определяется разделом `## Формат вывода — таблица тест-кейсов (ОБЯЗАТЕЛЬНО)` в `SKILL.md`.

### Тест-план

Определяется блоком «Deep Dive: Шаблон тест-плана» в `SKILL.md`: краткое резюме, объём, стратегия, окружение, критерии входа/выхода, оценка рисков, артефакты.

### Баг-репорт

Определяется блоком «Deep Dive: Баг-репортинг» в `SKILL.md`: правило заголовка (что + где + при каких условиях), окружение, описание, таблица «Шаги → Фактический результат → Ожидаемый результат», визуальные доказательства, доп. контекст.

### Отчёт о прогоне тестов

Обязательный формат — раздел `## Формат вывода — отчёт о прогоне тестов (ОБЯЗАТЕЛЬНО)` в `SKILL.md`: сводка, тест-кейсы по приоритету, критичные падения, заблокированные тесты, риски, следующие шаги, матрица покрытия. Скилл не выполняет тесты сам — отчёт заполняется реальными результатами прогона.

| Тест-план | 2–3 часа | 10–15 мин | 90% |
| 10 тест-кейсов | 1–2 часа | 5–10 мин | 85% |
| Регрессионный набор | 2–4 часа | 15–20 мин | 90% |
| Баг-репорт | 10–15 мин | 5 мин | 50% |
| Валидация Figma | 30–60 мин | 10–15 мин | 75% |

## Начало работы

1. Активируйте скилл: `/qa-test-planner`.
2. Опишите, что нужно (тест-план, тест-кейсы, баг-репорт и т.д.).
3. Проверьте и при необходимости скорректируйте результат.
4. Скопируйте в свою систему (Jira, Linear и т.д.).

## Поддержка

Подробности по каждому результату — в `SKILL.md`:
- Deep Dive по каждому типу результата.
- Готовые шаблоны с примерами.
- Процесс работы QA.
- Отслеживание выполнения тестов.
- Матрица покрытия.
