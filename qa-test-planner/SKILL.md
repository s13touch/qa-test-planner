# QA Test Planner

Комплексный скилл для QA-инженеров: создание тест-планов, генерация ручных тест-кейсов, построение регрессионных наборов, валидация дизайна по Figma и грамотное оформление багов.

> **Активация:** скилл срабатывает только при явном вызове по имени (например, `/qa-test-planner`, `qa-test-planner` или «используй скилл qa-test-planner»).

---

## Быстрый старт

**Создать тест-план:**
```
"Составь тест-план для функции авторизации пользователя"
```

**Сгенерировать тест-кейсы:**
```
"Сгенерируй ручные тест-кейсы для сценария оформления заказа"
```

**Собрать регрессионный набор:**
```
"Собери регрессионный набор для модуля оплаты"
```

**Сравнить с Figma:**
```
"Сравни страницу входа с макетом Figma по [URL]"
```

**Создать баг-репорт:**
```
"Создай баг-репорт по проблеме с валидацией формы"
```

---

## Краткая справка

| Задача | Что получаете | Время |
|------|--------------|------|
| Тест-план | Стратегия, объём, график, риски | 10–15 мин |
| Тест-кейсы | Пошаговые инструкции, ожидаемые результаты | 5–10 мин на кейс |
| Регрессионный набор | Smoke-тесты, критичные пути, порядок выполнения | 15–20 мин |
| Валидация Figma | Сравнение дизайна и реализации, список расхождений | 10–15 мин |
| Баг-репорт | Шаги воспроизведения, окружение, доказательства | 5 мин |

## Формат вывода — таблица тест-кейсов (ОБЯЗАТЕЛЬНО)

> Этот раздел определяет **только то, как подаются тест-кейсы**. Он перекрывает разметку вывода любого шаблона тест-кейсов в этом файле и в `references/`.
> Всё остальное руководство по тест-дизайну (типы тестов, покрытие, крайние случаи, приоритеты, техники) продолжает действовать — не повторяйте его здесь.
> Вход **не обязан** быть готовой таблицей требований — подойдёт любая доступная документация (спеки, user stories, дизайн, тикеты, описания, заметки со встреч).

### Правила подачи

- Если в источнике есть разделы/заголовки — группируйте тест-кейсы по ним и **сохраняйте исходные названия разделов**. Если источник неструктурирован — придумайте короткое описательное название раздела сами.
- Под каждым названием раздела выводите одну Markdown-таблицу ровно с этими 4 колонками, в таком порядке:

```
*Название раздела*

| № требования | Номер кейса | Приоритет | Описание тест-кейса |
| ------------ | ----------- | --------- | ------------------- |
| 12 | TC-01 | P0 | При нажатии на кнопку "Заключить договор" открывается модальное окно "Заключение договора". |
| 12 | TC-02 | P1 | [EP] При выборе типа договора "Стандартный" все поля формы отображаются корректно. |
```

Правила колонок:

- **№ требования** — идентификатор точно как в источнике (например, `12`). Если источник не является нумерованной таблицей требований — используйте ближайшую доступную ссылку (название раздела, ID истории/тикета) или `—`.
- **Номер кейса** — уникальный последовательный номер (`TC-01`, `TC-02`, …), сквозной по всем разделам (не перезапускается в каждом разделе).
- **Приоритет** — одно из `P0 | P1 | P2 | P3` (P0 — наивысший).
- **Описание тест-кейса** — краткое описание сценария (одно предложение). При необходимости можно префиксовать тег техники, например `[EP]` или `[BVA]`.

Ограничения формата:

- Повторяйте блок *заголовок раздела + таблица* для каждого раздела.
- НЕ добавляйте лишние колонки, заметки, предусловия или дополнительные разделы.

## Формат вывода — отчёт о прогоне тестов (ОБЯЗАТЕЛЬНО)

> Этот раздел определяет **обязательную структуру отчёта о прогоне тестов**. Он перекрывает шаблон в Deep Dive ниже и в `references/`.
> Соблюдайте его строго: не пропускайте секции, не переименовывайте их и не добавляйте свои.

```markdown
## Сводка
- Всего тест-кейсов: [N]
- Выполнено: [N]

- Провалено: [N]

- Не запускалось: [N]
- Pass Rate: [%]

| Приоритет | Всего | Pass | Fail | Заблокировано |
|----------|-------|------|------|---------|
| P0 (Critical) | [N] | [N] | [N] | [N] |
| P1 (High) | [N] | [N] | [N] | [N] |
| P2 (Medium) | [N] | [N] | [N] | [N] |
| P3 (Low) | [N] | [N] | [N] | [N] |

## Критичные падения
- TC-XX: [описание]
  - Баг: [BUG-ID]
  - Статус: [Open / In Progress / Fixed]

## Заблокированные тесты
- TC-XX: [причина]

## Риски
- [риск]

## Следующие шаги
- [шаг]

## Матрица покрытия

| Фича | Требований | Тест-кейсов | Статус | Пробелы |
|---------|--------------|------------|--------|------|
| [Фича] | [N] | [N] | Полное / Частичное / Нет | [Пробелы] |
```

### Правила заполнения

- Порядок и названия секций — строго как в шаблоне.
- Если данных нет — пишите `нет данных` или оставляйте `[N]`, но **секцию не удаляйте**.
- Номера тест-кейсов — наши `TC-XX` (сквозная нумерация из таблицы тест-кейсов).
- Все таблицы — Markdown; пустые ячейки не оставлять (писать `—` или `нет данных`).
- Скилл **не выполняет** тесты сам: отчёт заполняется реальными результатами прогона, которые предоставил пользователь.

## Основные результаты

### 1. Тест-планы
- Объём и цели тестирования
- Подход и стратегия тестирования
- Требования к окружению
- Критерии входа/выхода
- Оценка рисков
- Сроки и вехи

### 2. Ручные тест-кейсы
- Пошаговые инструкции
- Ожидаемый и фактический результаты
- Предусловия и подготовка
- Требования к тестовым данным
- Приоритет и серьёзность

### 3. Регрессионные наборы
- Smoke-тесты (15–30 мин)
- Полная регрессия (2–4 часа)
- Целевая регрессия (30–60 мин)
- Порядок выполнения и зависимости

### 4. Валидация Figma
- Сравнение по компонентам
- Проверка отступов и типографики
- Проверка цветов и визуальной согласованности
- Проверка интерактивных состояний

### 5. Баг-репорты
- Понятные шаги воспроизведения
- Детали окружения
- Доказательства (скриншоты, логи)
- Серьёзность и приоритет

## Антипаттерны

| Избегайте | Почему | Как надо |
|-------|-----|---------|
| Размытые шаги теста | Невозможно воспроизвести | Конкретные действия + ожидаемый результат |
| Отсутствие предусловий | Тесты неожиданно падают | Описывайте все требования к настройке |
| Нет тестовых данных | Тестировщик заблокирован | Давайте примеры данных или способ генерации |
| Общие заголовки багов | Трудно отслеживать | Конкретно: "[Фича] проблема при [действии]" |
| Пропуск крайних случаев | Пропуск критичных багов | Включайте граничные значения, null |

### Структура тест-плана

```markdown
# Тест-план: [Название фичи / релиза]

## Краткое резюме
- Что за продукт/фича тестируется
- Цели тестирования
- Ключевые риски
- Сроки (обзорно)

## Объём тестирования

**Входит в объём:**
- Фичи, которые тестируем
- Типы тестов (функциональные, UI, производительность)
- Платформы и окружения
- Пользовательские сценарии

**Не входит в объём:**
- Фичи, которые не тестируем
- Известные ограничения
- Сторонние интеграции (если применимо)

## Стратегия тестирования

**Типы тестов:**
- Ручное тестирование
- Исследовательское тестирование (exploratory)
- Регрессионное тестирование
- Интеграционное тестирование
- Приёмочное тестирование (UAT)

**Подход:**
- Тестирование «чёрного ящика» (black box)
- Позитивные и негативные проверки
- Анализ граничных значений (BVA)
- Классы эквивалентности (EP)

## Тестовое окружение
- Операционные системы
- Браузеры и версии
- Устройства (мобильные, планшет, десктоп)
- Требования к тестовым данным
- Бэкенд / API-окружения

## Критерии входа
- [ ] Требования задокументированы
- [ ] Дизайн утверждён
- [ ] Тестовое окружение готово
- [ ] Тестовые данные подготовлены
- [ ] Сборка развёрнута

## Критерии выхода
- [ ] Выполнены все высокоприоритетные тест-кейсы
- [ ] Пройдено 90%+ тест-кейсов
- [ ] Все критичные баги исправлены
- [ ] Нет открытых багов высокой серьёзности
- [ ] Пройден регрессионный набор
```

<summary><strong>Deep Dive: Баг-репортинг</strong></summary>

### Правило заголовка

Заголовок обязан отвечать на три вопроса — **что произошло**, **где произошло** и **при каких условиях** — и при этом быть кратким и лаконичным (одна строка).

Формат: `[Что произошло] + [где] + [при каких условиях]`

- Плохо: `Баг с будильником`
- Хорошо: `Будильник звенит дважды на странице будильников после нажатия «Отложить»`

### Шаблон баг-репорта

```markdown
# BUG-[ID]: [Что произошло + где + при каких условиях]

**Серьёзность:** Critical | High | Medium | Low
**Приоритет:** P0 | P1 | P2 | P3
**Тип:** Functional | UI | Performance | Security
**Статус:** Open | In Progress | Fixed | Closed

## Окружение
- **ОС:** [Windows 11, macOS 14 и т.д.]
- **Браузер:** [Chrome 120, Firefox 121 и т.д.]
- **Устройство:** [Десктоп, iPhone 15 и т.д.]
- **Сборка:** [Версия/коммит]
- **URL:** [Страница, где воспроизводится баг]

## Описание
[Понятное краткое описание проблемы]

## Шаги и результаты

| Шаги воспроизведения | Фактический результат | Ожидаемый результат |
| --- | --- | --- |
| 1. [Конкретный шаг]<br>2. [Конкретный шаг]<br>3. [Конкретный шаг] | [Что происходит на самом деле] | [Что должно происходить] |

## Визуальные доказательства
- Скриншот: [приложен]
- Видео: [ссылка, если есть]
- Ошибки консоли: [вставить ошибки]

## Дополнительный контекст
- Связано с: [Фича/тикет]
- Регресс: [Да/Нет]
- Макет Figma: [Ссылка, если UI-баг]
```

### Определения серьёзности

| Уровень | Критерии | Примеры |
|-------|----------|----------|
| **Critical (P0)** | Падение системы, потеря данных, безопасность | Оплата не проходит, вход сломан |
| **High (P1)** | Крупная фича сломана, нет обходного пути | Поиск не работает |
| **Medium (P2)** | Фича работает частично, есть обходной путь | В фильтре нет одной опции |
| **Low (P3)** | Косметика, редкие крайние случаи | Опечатка, мелкое выравнивание |

<summary><strong>Deep Dive: Интеграция с Figma MCP</strong></summary>

### Процесс валидации дизайна

**Предусловия:**
- Настроен Figma MCP сервер
- Есть доступ к файлам дизайна Figma
- Есть Figma-ссылки на компоненты/страницы

**Процесс:**

1. **Получить спецификации из Figma**
```
"Получи спецификации кнопки из Figma-файла [URL]"

Ответ содержит:
- Размеры (ширина, высота)
- Цвета (фон, текст, граница)
- Типографику (шрифт, размер, начертание)
- Отступы (padding, margin)
- Скругление углов
- Состояния (default, hover, active, disabled)
```

2. **Сравнить с реализацией**
```
ТК: Визуальная валидация основной кнопки
1. Открыть основную кнопку в dev tools браузера
2. Сравнить со спецификациями Figma:
   - Размеры: 120x40px
   - Скругление: 8px
   - Цвет фона: #0066FF
   - Шрифт: 16px Medium #FFFFFF
3. Зафиксировать расхождения
```

3. **Создать баг при расхождении**
```
BUG: Цвет основной кнопки не совпадает с макетом
Серьёзность: Medium
Ожидаемо (Figma): #0066FF
Фактически (реализация): #0052CC
Скриншот: [приложен]
Ссылка на Figma: [конкретный компонент]
```

### Что проверять

| Элемент | Что проверять | Инструмент |
|---------|---------------|------|
| Цвета | Точные hex-значения | Пипетка браузера |
| Отступы | Padding/margin в px | Computed styles в DevTools |
| Типографика | Шрифт, размер, начертание | Панель Font в DevTools |
| Вёрстка | Ширина, высота, положение | Box model в DevTools |
| Состояния | Hover, active, focus | Ручное взаимодействие |
| Адаптивность | Поведение на breakpoints | Режим устройства в DevTools |

### Примеры запросов

<details>
<summary><strong>Deep Dive: Регрессионное тестирование</strong></summary>

### Структура наборов

| Тип набора | Длительность | Частота | Покрытие |
|------------|----------|-----------|----------|
| Smoke | 15–30 мин | Ежедневно | Только критичные пути |
| Targeted | 30–60 мин | На каждое изменение | Затронутые области |
| Full | 2–4 часа | Еженедельно/на релиз | Полное |
| Sanity | 10–15 мин | После хотфикса | Быстрая проверка |

### Построение регрессионного набора

**Шаг 1: Определить критичные пути**
- Без чего пользователи НЕ могут обойтись?
- Что приносит доход?
- Что работает с чувствительными данными?
- Что используется чаще всего?

**Шаг 2: Приоритизировать тест-кейсы**

| Приоритет | Описание | Когда запускать |
|----------|-------------|----------|
| P0 | Бизнес-критичное, безопасность | Всегда |
| P1 | Крупные фичи, частые сценарии | Еженедельно+ |
| P2 | Мелкие фичи, крайние случаи | На релизы |

**Шаг 3: Порядок выполнения**
1. Сначала Smoke — если провалился, остановиться и чинить сборку
2. Затем P0-тесты — должны пройти до продолжения
3. Потом P1 и P2 — фиксировать все падения
4. Исследовательское тестирование — искать неожиданные проблемы

### Критерии Pass/Fail

**PASS (успех):**
- Все P0-тесты пройдены
- 90%+ P1-тестов пройдено
- Нет открытых критичных багов

**FAIL (блокирует релиз):**
- Любой P0-тест провален
- Найден критичный баг
- Уязвимость безопасности
- Сценарий потери данных

**CONDITIONAL (условно):**
- Падения P1 с обходными путями
- Известные проблемы задокументированы
- Есть план исправления

</details>

<details>
<summary><strong>Deep Dive: Отслеживание выполнения тестов</strong></summary>

### Отчёт о прогоне тестов

Обязательный формат отчёта определён выше — в разделе «Формат вывода — отчёт о прогоне тестов (ОБЯЗАТЕЛЬНО)». Следуйте ему строго.

### Отслеживание покрытия

Матрица покрытия строится по фичам: сколько требований, сколько тест-кейсов, статус покрытия и пробелы. Она входит в обязательный шаблон отчёта (последняя секция).

### Показатели

- **Pass Rate** — доля пройденных от выполненных.
- **Заблокировано** — тесты, которые нельзя выполнить из-за окружения или зависимостей.
- **Пробелы покрытия** — требования без тест-кейсов.

</details>

<summary><strong>Лучшие практики</strong></summary>

### Написание тест-кейсов

**НУЖНО:**
- Быть конкретным и однозначным
- Указывать ожидаемый результат для каждого шага
- Проверять одну вещь на тест-кейс
- Использовать единые соглашения об именовании
- Поддерживать тест-кейсы в актуальном виде

**НЕЛЬЗЯ:**
- Предполагать наличие знаний
- Делать тест-кейсы слишком длинными
- Пропускать предусловия
- Забывать про крайние случаи
- Оставлять ожидаемый результат расплывчатым

### Баг-репортинг

**НУЖНО:**
- Давать понятные шаги воспроизведения
- Прикладывать скриншоты/видео
- Указывать точные детали окружения
- Описывать влияние на пользователей
- Ссылаться на Figma для UI-багов

**НЕЛЬЗЯ:**
- Сообщать о баге без шагов воспроизведения
- Использовать расплывчатые формулировки
- Пропускать детали окружения
- Забывать указать приоритет
- Дублировать существующие баги

### Регрессионное тестирование

**НУЖНО:**
- Автоматизировать повторяющиеся тесты, где возможно
- Регулярно поддерживать регрессионный набор
- Приоритизировать критичные пути
- Часто запускать smoke-тесты
- Обновлять набор после каждого релиза

**НЕЛЬЗЯ:**
- Пропускать регрессию перед релизами
- Давать набору устареть
- Тестировать всё каждый раз
- Игнорировать провалившиеся регрессионные тесты

</details>
