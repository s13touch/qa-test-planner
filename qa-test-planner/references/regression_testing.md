# Руководство по регрессионному тестированию

Стратегии и практики регрессионного тестирования.

> Формат тест-кейсов (`TC-XX`) и структура наборов описаны в `SKILL.md` (разделы «Формат вывода — таблица тест-кейсов» и «Deep Dive: Регрессионное тестирование»). Здесь — практическая часть: построение, примеры, выполнение, поддержка.

---

## Что такое регрессионное тестирование

**Определение:** повторная проверка существующего функционала, чтобы новые изменения ничего не сломали.

**Когда запускать:**
- перед каждым релизом;
- после исправления багов;
- после добавления новых фич;
- после рефакторинга;
- в еженедельных/ночных сборках.

---

## Построение регрессионного набора

### Шаг 1: определить критичные пути

Вопросы:
- Без чего пользователи точно НЕ могут обойтись?
- Что приносит доход?
- Что работает с чувствительными данными?
- Что используется чаще всего?

Примеры критичных путей:
- аутентификация пользователя;
- обработка оплаты;
- отправка данных;
- формирование отчётов;
- ключевая бизнес-логика.

### Шаг 2: приоритизировать тест-кейсы

- **P0 (обязательно):** бизнес-критичное, безопасность, целостность данных, фичи, влияющие на доход.
- **P1 (желательно):** крупные фичи, частые сценарии, точки интеграции, производительность.
- **P2 (по возможности):** мелкие фичи, крайние случаи, косметика UI.

### Шаг 3: сгруппировать по областям

```
Аутентификация и авторизация
├─ Вход/выход
├─ Сброс пароля
├─ Управление сессией
└─ Права доступа

Обработка оплаты
├─ Оформление заказа
├─ Способы оплаты
├─ Возвраты
└─ Формирование чеков

Управление пользователями
├─ Обновление профиля
├─ Настройки
├─ Параметры аккаунта
└─ Экспорт данных
```

## Примеры наборов

Идентификаторы кейсов соответствуют основному набору (`TC-XX` из таблицы тест-кейсов).

### E-commerce: Smoke-набор (20 мин)

```
TC-01: Главная страница загружается
TC-02: Пользователь может войти
TC-03: Поиск товаров работает
TC-04: Добавление в корзину работает
TC-05: Оформление заказа доступно
TC-06: Платёжный шлюз отвечает
```

### E-commerce: полная регрессия (3 часа)

**Аккаунт пользователя (30 мин):** регистрация, вход/выход, сброс пароля, обновление профиля, управление адресами.

**Каталог товаров (45 мин):** категории, поиск, фильтры и сортировка, карточка товара, зум изображений, отзывы.

**Корзина (30 мин):** добавление, изменение количества, удаление, применение скидок, «отложить», сохранение корзины.

**Оформление и оплата (45 мин):** гостевое оформление, оформление авторизованным пользователем, несколько адресов, способы оплаты, подтверждение заказа, email-уведомления.

**Управление заказами (30 мин):** история заказов, отслеживание, отмены, возвраты/возвраты средств, повторный заказ.

## Порядок выполнения

1. **Сначала Smoke** — если провалился, остановиться и чинить сборку; если прошёл — переходить к полной регрессии.
2. **Затем P0** — критичный функционал; должен пройти до продолжения.
3. **Потом P1 и P2** — выполнить остальное, фиксировать все падения.
4. **Исследовательское тестирование** — без сценариев, поиск неожиданных проблем.

> Критерии PASS / FAIL (блокирует релиз) / CONDITIONAL — см. `SKILL.md`, подраздел «Критерии Pass/Fail».

## Поддержка набора

**Ежемесячно:**
- удалять устаревшие тесты;
- обновлять изменённый функционал;
- добавлять новые критичные пути;
- оптимизировать медленные тесты.

**После каждого релиза:**
- обновлять тестовые данные;
- чинить сломавшиеся тесты;
- добавлять регрессию на найденные баги;
- документировать изменения.

---

## Автоматизация

**Хорошо подходит для автоматизации:**
- стабильные повторяющиеся тесты;
- smoke-тесты;
- API-тесты;
- проверки данных;
- кросс-браузерные проверки.

**Оставить ручным:**
- исследовательское тестирование;
- оценка удобства (usability);
- валидация визуального дизайна;
- сложные пользовательские сценарии.

## Отчёт о прогоне регрессии

Формат отчёта о прогоне единый — см. `SKILL.md`, подраздел «Шаблон отчёта о прогоне тестов». Для регрессии в отчёт добавляется итоговая рекомендация go/no-go:

**Рекомендация:** GO / УСЛОВНЫЙ GO / NO-GO
- Критичные баги (P0) исправить до релиза
- Падения P1 допустимы только при задокументированном обходном пути
- Перетестировать затронутые области после исправлений
- Финальный прогон регрессии перед продакшеном

---

## Типичные ошибки

**❌ Нельзя:**
- запускать одни и те же тесты без обновления;
- пропускать регрессию «чтобы сэкономить время»;
- игнорировать падения в низкоприоритетных тестах;
- тестировать только happy path;
- забывать обновлять тестовые данные;
- прогнать регрессию один раз и забыть.

**✅ Нужно:**
- регулярно поддерживать набор;
- запускать регрессию последовательно;
- разбирать все падения;
- включать крайние случаи;
- держать тестовые данные свежими;
- автоматизировать повторяющееся.

## Чек-лист регрессии

**Перед выполнением:**
- [ ] Тестовое окружение готово
- [ ] Сборка развёрнута
- [ ] Тестовые данные подготовлены
- [ ] Прошлые баги проверены как исправленные
- [ ] Набор отревьюен/обновлён

**Во время выполнения:**
- [ ] Соблюдать порядок выполнения
- [ ] Фиксировать все падения
- [ ] Скриншотить/записывать проблемы
- [ ] Отмечать неожиданное поведение
- [ ] Отслеживать блокеры

**После выполнения:**
- [ ] Собрать результаты
- [ ] Завести новые баги
- [ ] Обновить тест-кейсы
- [ ] Отчитаться стейкхолдерам
- [ ] Архивировать артефакты

## Быстрая справка

| Тип набора | Длительность | Частота | Покрытие |
|------------|----------|-----------|----------|
| Smoke | 15–30 мин | Ежедневно | Критичные пути |
| Targeted | 30–60 мин | На изменение | Затронутые области |
| Full | 2–4 часа | Еженедельно/релиз | Полное |
| Sanity | 10–15 мин | После хотфикса | Быстрая проверка |

**Помните:** регрессия — это страховка от поломки существующего функционала.
